# Recipe canonicalization

## Reproduce

From the repository root, using Python 3 (standard library only):

```powershell
python scripts/canonicalize_recipes.py
python scripts/canonicalize_recipes.py --check
python -m unittest discover -s tests -p 'test_recipe*.py' -v
python scripts/eda/recipe_name_alias_analysis.py --check
python scripts/audit_final_dataset.py
```

The first command regenerates the six canonicalization/application artifacts below.
`--check` regenerates in memory and compares every artifact, including the input
hash manifest, with disk without writing. Neither command changes source data,
ingredient aliases, master nutrition, or existing processed recipe exports.
No recommendation consumer is switched to these outputs by this change.

## Phase 1: safely normalized same-name grouping

Candidate names use Unicode NFC, lowercase, trimmed/collapsed whitespace.
Accents, punctuation and every word are retained. Different normalized names
are never merged. Blank names receive separate groups keyed by original ID.
The canonical dish name is the normalized source name, not an inferred label.

Each candidate group has exactly one quality-ranked representative. Singletons
map to themselves. This is representative selection, not an assertion that
the source records are interchangeable or exact duplicates.

The project lead's explicit business policy confirms every group sharing a
nonempty safely normalized dish name. These groups have
`resolution_status=automatic`, regardless of differing or empty ingredient-name
sets. Different ingredients, quantities, servings and preparation styles are
expected variants. Ingredient quality determines the representative using the
unchanged ranking below; ingredient similarity is not a grouping requirement.
This replaces the earlier ingredient-set review gate.

Manual review is reserved for structural ambiguity. A missing normalized name
prevents name-based grouping: that recipe maps to itself in an isolated group
with `resolution_status=provisional_review` and a missing-name reason. Review
evidence retains the source ID, name, ingredient text and matching information.
Missing/duplicate IDs or invalid references stop generation before writing, since
the pipeline cannot safely preserve provenance. Quality ties are resolved by ID
and do not require review. No fuzzy, semantic, or ingredient-alias grouping is
performed in Phase 1; differently normalized names join only through the reviewed Phase 2 layer below.

## Phase 2: manually reviewed recipe-name aliases

The 2026-09-10 business review approved 31 of the 32 discovered pairs and rejected
exactly one: **Mì trứng tôm thịt heo** / **Mì tôm Trứng Thịt heo**. Word order changes
the likely noodle-type interpretation. This rejection is a reviewed constraint,
not an exception hidden inside the lexical discovery rules.

`recipe_name_alias_decisions.json` is the explicit, versioned decision input. Each
relationship has both Phase 1 representative IDs, normalized names, approval or
rejection, and reason. Coverage must equal the candidate snapshot exactly;
duplicate decisions, unknown endpoints and changed ID/name associations fail.
The file records the business review date and is never regenerated by the pipeline.

Every run reconstructs Phase 1 from unchanged interim sources, then forms connected
components using only approved relationships. Rejected endpoints must remain in
different components, including through transitive paths; conflicts stop generation
before writing. All original recipes in a component compete under the unchanged
quality tuple and ID tie-breaker. Because this order is total and group-independent,
the winner is also the best Phase 1 representative in that component; this invariant
is checked. The selected source recipe's normalized name becomes the final dish name.

Merged groups have `resolution_status=reviewed_approved`. Final recipe and mapping
rows include `canonicalization_phase`, `phase1_canonical_recipe_id` and
`phase1_canonical_dish_name`. Group IDs encode the sorted member names; the mapping
retains every original recipe, including nonselected members of Phase 1 groups.
`duplicate_group_size` now counts all original recipes in the final group.
The application audit records both final target IDs for each approved/rejected edge.

The discovery CSV remains the original 32-pair evidence snapshot with its historical
unreviewed candidate status. The decision JSON and application audit are authoritative
for review outcomes. Discovery now reconstructs Phase 1 in memory, preserving its
input and candidate CSV even after final outputs shrink.

## Quality ranking

No weighted sum is used. The following tuple is maximized lexicographically:
an earlier criterion always wins before later criteria are considered. This
ordering prioritizes ingredient usability and master coverage as required by
`AGENTS.md`, followed by known quantity and nutrition limitations. Rates prevent
systematic preference for short ingredient lists; raw counts remain available
for audit. A longer recipe is not inherently more complete or better.

1. At least one ingredient row exists.
2. Ingredient coverage: count of nonempty cleaned names divided by the maximum
   of actual ingredient-row count, declared `ingredients_count`, and one.
   This measures observed row/name completeness, not culinary completeness.
3. Valid master-match rate: code exists in the master CSV, matching method is
   nonempty, and method is not `UNMATCHED`.
4. Lower explicit `UNMATCHED` rate, including unmatched rows that retain codes.
5. Lower fallback rate: nonpositive/missing/nonfinite required quantity **and**
   estimated weight exactly 10 g. Explicit quantities weighing 10 g are not
   called fallback. All 10 g rows are also counted separately.
6. Lower rate of nonpositive/missing/nonfinite required quantities.
7. Lower ingredient nutrition-anomaly rate. A row is counted once if any apply:
   missing/negative/nonfinite nutrition; invalid weight; total macro mass above
   weight plus 0.1 g rounding tolerance; absent master record; or invalid/missing/
   inconsistent master nutrition. Calorie inconsistency uses the existing EDA
   threshold: `abs(calories - (4*protein + 9*fat + 4*carbs))/calories > 0.30`.
   Zero calories with nonzero macro energy is also flagged. These are quality
   indicators, not clinical nutrition validation or silent repairs.
8. Fewer recipe nutrition flags: one for invalid/inconsistent recipe macros and
   one per total differing from ingredient sums. Sum tolerance is 0.1 per row
   because published totals/ingredient macros are rounded; stable summation is
   used. Missing values count as anomalies and are never repaired into zeros.
9. Positive, finite default servings.
10. Syntactically available HTTP(S) source URL with a hostname. No network check.
11. Ascending original recipe ID for remaining ties.

Rates use exact rational numbers during comparison. `selection_score` is a JSON
array of strings representing the ordered tuple (including negative penalty
rates), not a scalar, probability or calibrated confidence. Higher tuples are
better; parse fractions to compare, rather than sorting their string encodings.
`selection_reason` identifies the first distinction against the runner-up.
Mapping rows contain the candidate's own score, group rank and raw metrics,
alongside the selected recipe's score and rationale.

Qwen matching counts and unmatched-with-code counts remain visible. Hard-coded
Qwen confidence is not used as a probability. Catalog membership does not prove
a match is semantically correct. Existing false positives and zeros inherited
from missing master nutrition remain untouched. All-zero nutrition is not by
itself an error because some ingredients can legitimately have no macro energy.

## Artifacts and provenance

All artifacts are in `data/processed/recipes/`:

- `canonical_recipes.csv`: complete, unchanged source recipe columns plus
  canonical ID, normalized dish name, group ID, source URL, score, reason, group
  size and resolution status. Source `id` is retained as the canonical ID.
- `canonical_recipe_ingredients.csv`: all original ingredient columns and values
  for selected recipes only, plus canonical ID and dish name. Ingredient IDs and
  original recipe references remain intact.
- `recipe_canonical_mapping.csv`: exactly one row per original recipe, including
  singletons and all rejected candidates, with candidate quality audit fields.
- `recipe_canonical_review.csv`: one row per candidate requiring review, with
  the evidence described above and the isolated representative. When no review
  is needed, the CSV contains only its complete header, preserving its schema.
- `recipe_canonicalization_summary.json`: counts, validation result, SHA-256
  digests of canonical CSVs, every raw/interim file, aliases, master nutrition
  and the four pre-existing processed recipe exports. No timestamps.
- `recipe_name_alias_application_audit.csv`: all 32 reviewed edges, their reasons,
  and final canonical targets; rejected endpoints remain different.
- `recipe_name_alias_decisions.json`: reviewed input, never overwritten by generation.

Summary top-level counts describe the final combined groups. Nested `phase1` preserves
the original same-name counts; `phase2` reports approved/rejected edges, reductions
and transitive components. Reviewed groups are counted separately from automatic
same-name groups. The summary also hashes the exact reviewed decision file.

CSV values are preserved as strings, avoiding numeric inference that could
change IDs, blanks or source nutrition. CSV formatting is deterministic UTF-8
with LF line endings. Recipe rows are sorted by source ID and ingredient rows
by recipe ID then ingredient ID.

## Validation

Generation validates unique source recipe/ingredient IDs and master codes,
source ingredient references, one selected ID per group, unique canonical IDs,
complete mapping coverage, valid mapping targets, singleton retention, and exact
preservation of selected source values and ingredient rows before writing.
It independently rebuilds from reversed input rows and compares serialized CSV
bytes and summary counts. Protected file hashes are checked before/after
generation and after writing, and output bytes are read back. A separate
`--check` run verifies repeatability against artifacts on disk.

Twenty-four focused unittest regressions passed, covering conservative normalization,
selection over ID order, unmatched rows retaining codes, explicit versus fallback
10 g weights, missing master nutrition, invalid references, singleton and blank
name handling, automatic confirmation despite different/empty ingredient sets,
separation of different names, stable empty-review CSV schema, source immutability,
and input permutation. Both requested generation and `--check` commands passed.
Additional tests cover approved token reorderings, punctuation and parenthetical
synonyms, the explicit rejected noodle pair, complete original-ID provenance,
transitive components and transitive rejection conflicts, stale decisions, and
permuted input/decision ordering. Before/after hashes confirm unchanged protected
sources, ingredient aliases, master nutrition and candidate/decision inputs.

The existing `scripts/audit_final_dataset.py` completed successfully: 5,641
original unique recipe IDs, 63,943 original ingredient rows, zero orphans, and
matching interim/processed counts. Its broad printed production-readiness claim
is not adopted here; the EDA's known quality problems remain present.
The pytest-based integrity suite could not run because this Python environment
has no pytest installed; the new tests ran through standard-library unittest.
